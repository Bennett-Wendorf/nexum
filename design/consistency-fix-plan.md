## Design Consistency Fixes (8 Issues)

### Issue 1: Unify Status Sets

**Problem:** Task status values were inconsistent between `persistence.md` and `work-statuses.md`. The `persistence.md` task template used `queued | planning | running | reviewing | completed | abandoned`, while `work-statuses.md` defined a more complete set including `waiting-manual-review` and `merge-queue`.

**Files Modified:**
- `design/persistence.md`
- `design/work-statuses.md`

**Changes Made:**
- Replaced the task status set in the `task.md` template with the canonical set: `backlog | queued | running | reviewing | waiting-manual-review | merge-queue | abandoned | completed`.
- Added a status value comment above `status.json` schema: `<!-- Status values: backlog | queued | running | reviewing | waiting-manual-review | merge-queue | abandoned | completed -->`.
- Normalized all status names to lowercase with hyphens (e.g., `waiting-manual-review`, `merge-queue`).
- Updated `task_status_map` example in `execution.json` to use canonical statuses.

**Cross-References Added:**
- `persistence.md` → `work-statuses.md` (Status machines section explicitly references the separate status machines for plans and tasks).

### Issue 3: Clarify Plan vs. Task Status Boundary

**Problem:** `work-statuses.md` listed "Pre-planning" and "Post-planning" statuses without clearly indicating that pre-planning statuses apply to plans and post-planning statuses apply to tasks. Both phases shared status names like `Planning` and `Reviewing`, creating ambiguity.

**Files Modified:**
- `design/work-statuses.md`
- `design/persistence.md`

**Changes Made:**
- Replaced the "Pre-planning" / "Post-planning" sections in `work-statuses.md` with explicit "Plan-level statuses" and "Task-level statuses" headings.
- Added clarifying note under task-level statuses: "These statuses apply to individual tasks within a plan. Plan-level statuses are defined separately above."
- Added a new "Status machines" section in `persistence.md` stating: "Plans and tasks have separate status machines" with explicit lists for each.

**Cross-References Added:**
- `persistence.md` Status machines section → `work-statuses.md` ("See work-statuses.md for the full status lifecycle definitions.").

### Issue 5: Consolidate Overlord Responsibilities

**Problem:** The Overlord role was vaguely defined with uncertain scope ("maybe not needed?"). Responsibilities scattered across documents were not consolidated in a single authoritative definition.

**Files Modified:**
- `design/agent-roles.md`
- `design/persistence.md`

**Changes Made:**
- Replaced the Overlord description with a hybrid model split into two sub-roles:
  - **Deterministic core** (rules-based, no LLM): status transitions, ID generation, concurrency enforcement, stale heartbeat detection, dependency-based auto-queue, branch merging.
  - **Agent layer** (LLM-powered): user interaction, prioritization, exception handling. Cannot execute tasks directly.
- Added cross-reference in `persistence.md` ID scheme section: "IDs are generated by the Overlord deterministic core (see agent-roles.md)."
- Added cross-reference in `persistence.md` Recovery section: "Stale lease detection is performed by the Overlord deterministic core (see agent-roles.md)."

**Cross-References Added:**
- `persistence.md` (ID scheme) → `agent-roles.md` (Overlord deterministic core).
- `persistence.md` (Recovery) → `agent-roles.md` (Overlord deterministic core).
- `agent-roles.md` (Overlord) → `work-statuses.md`, `persistence.md`, `resource-constraints.md`, `unit-of-work.md`.

### Issue 6: Connect Concurrency Limits

**Problem:** `resource-constraints.md` mentioned concurrency limits but did not explain who enforces them, how they are enforced, or which statuses are affected. No cross-references connected the three relevant documents.

**Files Modified:**
- `design/resource-constraints.md`
- `design/work-statuses.md`
- `design/persistence.md`

**Changes Made:**
- Expanded `resource-constraints.md` with a "Parallel agent limits" section detailing: enforcement mechanism (Overlord deterministic core checks `execution.json`), configurability per plan, concurrency-sensitive statuses, and enforcement authority.
- Updated concurrency-sensitive status list to distinguish plan-level (`planning`, `reviewing`) from task-level (`reviewing`, `running`).
- Added cross-references to `resource-constraints.md` in `work-statuses.md` status descriptions.
- Added comment in `persistence.md` execution.json concurrency block: "// Concurrency limits enforced by Overlord deterministic core before task dispatch. See resource-constraints.md."

**Cross-References Added:**
- `work-statuses.md` → `resource-constraints.md` ("See resource-constraints.md for enforcement details.").
- `persistence.md` (execution.json concurrency) → `resource-constraints.md`.
- `resource-constraints.md` → `persistence.md` (execution.json), `work-statuses.md`.
