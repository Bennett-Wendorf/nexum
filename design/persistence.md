# Persistence — Task & Plan Storage on Disk

## Guiding principles (from existing design)

- **Markdown is source of truth** — human-readable, agent-readable, interoperable
- **No database** — everything lives as files in the repo
- **Must work with multiple agents** — no agent-specific assumptions
- **Every level manually manageable** — baby-step mode means a human can edit any file and the system should respect it
- **Multi-repo, multi-branch** — scope can go wide

---

## Directory layout

```
<repo>/
  .agent/
    specs/                                      # Plans & task definitions (committed to repo)
      <branch-name>/                            # Organized by branch for archiving
        <plan-id>-<plan-name>/                  # Plan = group of tasks
          plan.md                              # The plan document (human-readable)
          tasks/                               # Sub-tasks generated by the planner
            <task-id>-<task-name>/
              task.md                          # Task definition (scope, acceptance criteria, background)
              status.json                      # Machine control-plane metadata (NOT committed)
    state/                                     # Runtime state (NOT committed, .gitignore'd)
      <branch-name>/                            # Mirrors specs/ branch organization
        <plan-id>-<plan-name>/
          execution.json                       # Agent leases, timestamps, queue state
          logs/
            <task-id>-<task-name>/
              run-1.log
              run-2.log
```

### Naming convention

Directories use `<id>-<slug>` format for both uniqueness and readability:

- `PLAN-001-oauth2-flow` — plan ID + descriptive name
- `TASK-001-auth-middleware` — task ID + descriptive name

The slug is a kebab-case summary. The ID provides stable references for cross-linking.

### Why split `specs/` vs `state/`?

- **`specs/`** is the *specification* — what work needs to be done. Organized by branch, lives in the repo, can be reviewed in PRs, survives restarts, other agents can read it.
- **`state/`** is the *execution context* — who's doing what right now, when did it start, what logs were produced. Ephemeral, not committed. Mirrors the branch organization of specs.

## File formats

### `task.md` — Individual task definition

```markdown
# TASK-001: Setup authentication middleware

**Parent plan:** PLAN-001
**Dependencies:** none
**Status:** backlog | queued | running | reviewing | waiting-manual-review | merge-queue | abandoned | completed

## Description
<What needs to be done>

## Acceptance criteria
- Middleware intercepts unauthenticated requests
- Returns 401 with proper JWT validation
- Unit tests pass

## Files to modify
- `src/middleware/auth.ts`
- `tests/middleware/auth.test.ts`

## Background
<Prior art, related tasks, architectural decisions, research findings>

## Notes
<Anything the builder agent should know>
```

## Status machines

Plans and tasks have separate status machines:

- **Plan statuses**: `backlog`, `queued`, `planning`, `reviewing`, `plan-complete` — apply to plan-level work items
- **Task statuses**: `backlog`, `queued`, `running`, `reviewing`, `waiting-manual-review`, `merge-queue`, `abandoned`, `completed` — apply to individual tasks within a plan

See work-statuses.md for the full status lifecycle definitions.

---

## ID scheme
IDs are generated by the Overlord deterministic core (see agent-roles.md).

- Plans: `PLAN-<NNN>` (sequential per branch)
- Tasks: `TASK-<NNN>` (sequential per plan)
- IDs are stable — once assigned, they don't change
- Generated by the overlord/planner when creating new work

Directory names embed both ID and human-readable slug:
- `PLAN-001-oauth2-flow`
- `TASK-001-auth-middleware`

This means you can find a task's location just from its name: `.agent/specs/<branch>/PLAN-001-oauth2-flow/tasks/TASK-001-auth-middleware/`

## Questions & open decisions

### 1. Where does `.agent/` live?

**✅ Decision: Option A — Inside the repo root.**

`.agent/specs/` contains committed markdown, organized by branch. `.agent/state/` is gitignored, as are all `status.json` files within specs.

```
# .gitignore
.agent/state/
.agent/specs/**/*.status.json
.agent/specs/**/tasks/**/status.json
```

Only the markdown specs (`plan.md`, `task.md`) are committed — human-readable, agent-readable, reviewable in PRs. The developer controls what gets tracked.

### 2. How do we handle multi-branch?

**✅ Decision: Branch is both a path segment and metadata.**

Each plan lives under `.agent/specs/<branch>/` and `.agent/state/<branch>/`. The branch name is also declared in `plan.md` metadata for portability — if a plan directory is moved or archived, the branch reference travels with it. The branch directory level enables easy organization and archiving of completed branches.

### 3. How do we handle concurrency safely with flat files?

**✅ Decision: Atomic rename + optimistic locking.**

All JSON state files are written via atomic rename: write to a temp file, then `os.rename()` into place. Rename is a single atomic syscall — the file either has the old content or the new content, never a partial write.

For task claiming, agents use optimistic locking:
1. Read `status.json`, check status is `"queued"`
2. Atomically write new status `"running"` with agent lease via temp + rename
3. If another agent beat you to it, the status will be `"running"` — back off and pick another task

No file locks needed. The race window is tiny (milliseconds) and agents naturally resolve contention by retrying.

### 4. Branch strategy

**✅ Decision: One plan branch + per-task ephemeral worktrees.**

- Each plan has one branch (e.g., `feature/auth-overhaul`) — this is the source of truth
- Each task gets its own **local branch + worktree** (`task/TASK-001`) spawned from the plan's branch
- Tasks work in complete isolation — no cross-talk between worktrees
- When a task finishes, the overlord merges its branch into the plan's branch
- The dependency graph dictates merge order — TASK-003 can't merge until TASK-001 and TASK-002 are merged
- After merge, the task branch is deleted and the worktree is cleaned up
- **Task branches are never pushed to remote** — they are a local, ephemeral concept for parallelization only

### 5. Orchestration hierarchy

**✅ Decision: Repo → Branch → Plan → Task. No epic layer.**

The directory structure mirrors the hierarchy: `.agent/specs/<branch>/<plan>/tasks/<task>/`. If grouping plans is needed later, it can be done via metadata labels rather than additional directory levels.

### 6. Diff tracking for plans

**✅ Decision: Git is sufficient.**

Markdown specs are committed, so `git log .agent/specs/<branch>/PLAN-001/` gives full history. For runtime state changes, `status.json` transitions log already tracks who did what and when. No separate changelog needed.

### 7. Agent team assignment

**⏸ Deferred.** Agent assignment is deterministic and will be designed separately. Not part of the persistence layer spec.

## Runtime concerns

### Atomic writes
All JSON state files should be written atomically:
```
write(temp_file) → rename(temp_file, target)
```
Prevents reading partial writes during concurrent access.

### Recovery
- If an agent dies mid-task, `status.json` still shows `running` with a `leased_at` timestamp
- Overlord detects stale leases (e.g., > 30 min since last heartbeat) and re-queues
- Stale lease detection is performed by the Overlord deterministic core (see agent-roles.md).
- `status.json` should include `heartbeat_at` that agents update periodically

### Heartbeat mechanism
- Agents update `heartbeat_at` in `status.json` every N minutes
- Overlord scans for stale heartbeats and recovers orphaned tasks
- Alternative: use file system `mtime` instead of embedding timestamp
