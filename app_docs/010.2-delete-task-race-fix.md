# Delete Task Race Condition Fix (Spec 010.2)

## Overview

The `delete_task` handler in `src/api/tasks.rs` previously performed three separate read-modify-write cycles without any concurrency protection. This allowed concurrent handlers to interleave their mutations, corrupting the plan's task list or the execution state's `task_status_map`. The fix wraps all three mutation phases under a single per-plan lock acquisition, serializing all mutations on a given plan.

## What Was Built

A per-plan lock guard was inserted into the `delete_task` handler (lines 413-415 in `src/api/tasks.rs`) that covers the entire mutation critical section — directory removal, plan file update, and execution state update. The lock infrastructure itself (`AppState.plan_locks`, the `lock_plan()` middleware helper) was provided by spec 010.1; this spec applied it specifically to `delete_task`.

### The TOCTOU Race Condition

Before the fix, `delete_task` performed three independent read-modify-write cycles:

```rust
// Phase 1: Remove task directory (filesystem mutation)
crate::persistence::remove_dir_all(&task_dir)?;

// Phase 2: Read plan, modify task list, write back
let mut plan = read_plan(...)?;
plan.tasks.retain(|t| t.id != resolved_task_id);
update_plan(...)?;

// Phase 3: Read execution state, modify task_status_map, write back
let mut exec_state = read_execution_state(...)?;
exec_state.tasks.retain(|t| *t != resolved_task_id);
exec_state.task_status_map.remove(&resolved_task_id);
update_execution_state(...)?;
```

Between any of these phases, a concurrent handler could read the same plan or execution state, apply its own modifications, and write back — overwriting the first handler's changes. Specific scenarios:

- **Concurrent `delete_task` on same plan**: One handler's deletion is overwritten by the other.
- **Concurrent `create_task` on same plan**: A deleted task reappears in the plan's task list.
- **Concurrent `transition_task_status` on same plan**: A deleted task retains a stale status entry in `task_status_map`.

The execution state race was particularly dangerous because, unlike `add_task_to_execution` (which has file-content-based TOCTOU protection at the persistence layer), `read_execution_state` + `update_execution_state` had **no** concurrency protection at the persistence layer.

### The Fix: Per-Plan Lock

The lock is acquired after path resolution (read-only filesystem operations) and before any mutations:

```rust
// Acquire per-plan lock to prevent TOCTOU race on plan read-modify-write
let plan_mutex = lock_plan(&state, &plan_id).await;
let _plan_guard = plan_mutex.lock().await;

// All three mutation phases are now serialized:
// Phase 1: remove_dir_all(...)
// Phase 2: read_plan -> retain -> update_plan
// Phase 3: read_execution_state -> retain + remove -> update_execution_state
```

The `_plan_guard` holds the lock for the remainder of the function scope. When the function returns, the guard is dropped and the mutex is released (Rust drop semantics).

### Three Mutation Phases Covered by the Lock

1. **Task directory removal** (`remove_dir_all` at line 418) — deletes the task's filesystem artifacts
2. **Plan file modification** (`read_plan` → `retain` → `update_plan` at lines 421-425) — removes the `TaskReference` from the plan's task list
3. **Execution state modification** (`read_execution_state` → `retain` + `remove` → `update_execution_state` at lines 428-439) — removes the task from `task_status_map`

Under the lock, all three phases are atomic with respect to other handlers on the same plan. No handler can observe an intermediate state where the task is deleted from one data store but not the other.

### Relationship to Spec 010.1 (Per-Plan Locking Infrastructure)

This fix reuses the infrastructure established by spec 010.1:

- **`AppState.plan_locks`** (`src/api/types.rs`): A `HashMap<String, Arc<tokio::sync::Mutex<()>>>` mapping plan IDs to per-plan async mutexes, wrapped in an outer `RwLock` for safe concurrent access to the map itself.
- **`lock_plan()`** (`src/api/middleware.rs`): Helper that lazily creates or retrieves the per-plan mutex for a given `plan_id`.

The locking design uses two levels:
- **Outer `RwLock`**: Protects the `HashMap` itself — held only for microseconds during lookup/insertion.
- **Inner `Mutex<()>`**: Serializes read-modify-write on a specific plan's files — held for milliseconds during file I/O.

This spec added `delete_task` to the roster of handlers protected by the per-plan lock, alongside `create_task`, `update_plan`, and `transition_plan_status` (all locked by spec 010.1).

## Usage

No user-facing changes. The fix is transparent to API callers. The `DELETE /api/branches/{branch}/plans/{plan_id}/tasks/{task_id}` endpoint behaves identically — it still removes the task and returns **204 No Content** on success. The difference is that concurrent deletions (or mixed deletions with creates/status transitions) on the same plan are now serialized rather than racing.

## Configuration

No configuration changes. The lock infrastructure is managed entirely at runtime through `AppState`. No environment variables or config fields are involved.
