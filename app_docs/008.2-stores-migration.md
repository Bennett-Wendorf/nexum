# 008.2 — Stores Migration

## Overview

Migrated the Nexum frontend from global Svelte writable stores to component-local reactive state. The previous `store.ts` module exported 10 writable stores that were mutated directly from components via `.set()`, creating tightly coupled components and unpredictable re-rendering behavior — an anti-pattern in Svelte 5, which favors component-local state and explicit data flow.

## What Was Built

The migration eliminated the global mutable store anti-pattern through three changes:

1. **Component-local state** — All four page components now use local `let loading = false` and `let error = $state<string | null>(null)` instead of reading/writing global `loading` and `error` stores.

2. **Lightweight error utility** — A new `errorUtils.ts` module provides a callback-based `setError()` function that each component uses with its own local error state variable. Errors auto-clear after 5 seconds, and a cleanup function prevents memory leaks.

3. **localStorage persistence** — `TaskList.svelte` replaced the global `viewMode` store with a localStorage-backed `$state` variable, preserving the kanban/list preference across page reloads.

Six stores (`currentPlan`, `currentBranch`, `currentTask`, `runningTasks`, `agents`, `tasks`) were identified as completely unused and deleted without migration. The `plans` store was written but never read by any component, so its write call was removed.

### Key API: `setError()`

The `errorUtils` module exports a single function:

```ts
export function setError(
  onSet: () => void,
  onClear: () => void,
  delayMs: number = 5000
): () => void
```

**Pattern**: Components declare their own `$state` error variable and pass setter/clearer callbacks:

```svelte
<script lang="ts">
  import { onCleanup } from 'svelte';
  import { setError } from '$lib/errorUtils';

  let error = $state<string | null>(null);

  function handleError(message: string): void {
    const cleanup = setError(
      () => { error = message; },
      () => { error = null; }
    );
    onCleanup(cleanup);
  }
</script>
```

**Behavior**:
- `onSet()` is called immediately to set the error message
- After `delayMs` milliseconds (default 5 seconds), `onClear()` is called to reset the error
- Returns a cleanup function that cancels the pending timeout — call it on component cleanup to prevent memory leaks

**Why this pattern**: Unlike the originally planned `createErrorState()` factory, the callback-based approach avoids importing Svelte runes into a plain `.ts` utility file. Each component owns its own `$state` variable, keeping the utility dependency-free and reusable in any context.

## Usage

### Error handling in page components

Every page follows the same pattern:

1. Import `setError` from `$lib/errorUtils`
2. Declare a local error state: `let error = $state<string | null>(null)`
3. In error handlers, call `setError(() => { error = message; }, () => { error = null; })`

### View mode persistence (TaskList only)

The kanban/list view mode preference is stored in localStorage under the key `nexum-viewMode`. The component reads this on initialization and writes back on every toggle:

```ts
const savedViewMode = localStorage.getItem('nexum-viewMode');
let viewMode = $state<'kanban' | 'list'>(
  (savedViewMode === 'kanban' || savedViewMode === 'list') ? savedViewMode : 'kanban'
);

function toggleView(): void {
  viewMode = viewMode === 'kanban' ? 'list' : 'kanban';
  localStorage.setItem('nexum-viewMode', viewMode);
}
```

## Configuration

No new configuration options or environment variables were introduced. The only persistent storage used is the `nexum-viewMode` localStorage key for the TaskList view mode preference.

## Code Review Findings Actioned

The following issues were identified during code review and resolved during this task:

| Finding | Resolution |
|---------|-----------|
| **errorUtils redesign** | The originally planned `createErrorState()` factory (which used `$state()` inside a `.ts` file) was replaced with a callback-based `setError()` pattern that keeps the utility dependency-free and avoids importing Svelte runes into a non-Svelte module. |
| **localStorage validation** | The `viewMode` localStorage read validates that the stored value is either `'kanban'` or `'list'` before use, falling back to `'kanban'` for any invalid or missing value. |
| **Empty status guard** | `TaskList.svelte` uses `tasksByStatus[status] ?? []` to provide empty arrays for statuses with no tasks, preventing `undefined` iteration errors in kanban columns. |
| **Hex color fix** | Status badge hex colors were corrected during the broader Svelte 5 migration (008.1) and carried through this task. |
| **`className` → `class` rename** | `RouterLink.svelte` was updated to use `class: classStr` prop destructuring (Svelte 5 reserved keyword pattern) instead of `className`. |

## Relationship to Plan 008.3

This migration is the second step in a three-part Svelte 5 frontend modernization:

1. **008.1 (Svelte 5 Runes Migration)** — Converted `$:` to `$derived`, `export let` to `$props()`, `on:event` to `onevent`.
2. **008.2 (Stores Migration)** — This feature. Removed global writable stores in favor of component-local state.
3. **008.3 (State Rune Migration)** — Runs next. Converts remaining non-reactive `let` variables in page components to `$state()` so that `$derived` values update correctly when data is assigned in `onMount`.

Plan 008.3 explicitly depends on 008.2 being complete. It notes that the `error` variable in each page is already declared as `$state<string | null>(null)` from this migration and requires no further changes. The remaining 12 non-reactive variables (`planList`, `plan`, `tasks`, `task`, `loading`, `activeTab`, `transitioning`, etc.) across the four page files will be converted to `$state()` in 008.3.
