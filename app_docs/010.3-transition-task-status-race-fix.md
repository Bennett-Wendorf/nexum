# 010.3 — TOCTOU Race Fix: Per-Plan Locking for Task Handlers

## Overview

Fixes a Time-of-Check-to-Time-of-Use (TOCTOU) race condition in four task-related API handlers: `create_task`, `delete_task`, `transition_task_status`, and `claim_task`. Before this fix, the separate persistence updates each handler performs — such as writing a task's `status.json` and then updating `task_status_map` in `execution.json`, or modifying the plan's task list and then the execution state — could interleave with concurrent handlers on the same plan, causing `task_status_map` to lag behind individual `status.json` files or the plan's task list to become inconsistent with the execution state.

## What Was Built

All four task handlers in `src/api/tasks.rs` — `create_task`, `delete_task`, `transition_task_status`, and `claim_task` — were wrapped with the per-plan locking infrastructure established by spec 010.1. Each handler now acquires a single per-plan mutex **before** any persistence mutations and holds it through **all** mutations (status.json writes, plan task-list updates, and task_status_map changes), serializing all mutations on a given plan.

### The Race Condition

Before the fix, each handler performed multiple separate persistence updates with no coordination:

```
1. update_task_status(...)       → writes status.json (has its own TOCTOU protection)
2. read_execution_state(...)     → reads execution.json
3. task_status_map.insert(...)   → modifies in-memory map
4. update_execution_state(...)   → writes execution.json (no concurrency protection)
```

A concurrent handler on the same plan could read intermediate state between steps, make its own modifications, and write them back — overwriting the first handler's updates. The result: one persistence artifact (e.g. `status.json` or the plan's task list) reflects the correct state, but another (e.g. `task_status_map` in `execution.json`) does not.

### How the Per-Plan Lock Prevents Interleaving

The fix uses the `lock_plan()` middleware helper (from spec 010.1) to acquire a per-plan `Mutex` before any mutations. Since the lock is scoped to the plan ID, concurrent operations on **different** plans proceed unimpeded, while operations on the **same** plan are serialized.

### Consistency Guarantee

Under the per-plan lock, `status.json` and `task_status_map` are updated atomically from the perspective of concurrent handlers. No handler can observe an intermediate state where `status.json` has been updated but `task_status_map` has not (or vice versa).

### Affected Handlers

1. **`create_task`** (lines 237–310) — Creates a task, updates plan task list and execution state.
2. **`delete_task`** (lines 402–442) — Removes a task, updates plan task list and execution state.
3. **`transition_task_status`** (lines 457–538) — Transitions a task to a new status.
4. **`claim_task`** (lines 554–674) — Claims (leases) a task for agent execution.

### Lock Acquisition Point

In all four handlers, the lock is acquired **after** `resolve_plan_path` and `resolve_task_path` (read-only filesystem operations) and **before** any persistence operations:

```rust
let plan_mutex = lock_plan(&state, &plan_id).await;
let _plan_guard = plan_mutex.lock().await;
```

This minimizes lock hold time by excluding path resolution from the critical section.

### Lock Scope

**`create_task`** — The guard covers:
- Task ID generation
- Task persistence (task.md + initial status.json)
- `read_task_status` (readback of created status)
- `read_plan` → append `TaskReference` → `update_plan` (plan task-list read-modify-write)
- `add_task_to_execution` (execution state read-modify-write to populate `task_status_map`)
- `read_task` (final read for response)

**`delete_task`** — The guard covers:
- Task directory removal
- `read_plan` → remove `TaskReference` → `update_plan` (plan task-list read-modify-write)
- `read_execution_state` → remove from `tasks` list + `task_status_map` → `update_execution_state` (execution state read-modify-write)

**`transition_task_status`** — The guard covers:
- `read_task_status` (validation read)
- `update_task_status` (status.json write with file-level TOCTOU protection)
- `read_execution_state` → `task_status_map.insert` → `update_execution_state` (execution state read-modify-write)
- `read_task` (final read for response)

**`claim_task`** — The guard covers:
- `read_task_status` (validation read)
- `update_task_status` (status.json write with file-level TOCTOU protection)
- Agent lease re-read and re-write of status.json (additional TOCTOU verification)
- `read_execution_state` → `task_status_map.insert` → `update_execution_state` (execution state read-modify-write)
- `read_task` (final read for response)

The guard is dropped automatically at end of function scope via Rust drop semantics.

### Key Design Decisions

- **No persistence layer changes**: The per-plan lock operates at the API handler level, serializing callers. Persistence functions remain unchanged.
- **Per-plan granularity**: The correct granularity because the race involves concurrent access to a single plan's `status.json` files and its `execution.json` `task_status_map`.
- **No deadlock risk**: Each handler acquires exactly one per-plan lock, held for a bounded duration. No nested locks.
- **Minimal performance impact**: The mutex is only held during file I/O. Concurrent operations on different plans are not blocked.

## Usage

No configuration or API changes are required. The fix is transparent to callers — all four task endpoints (`create_task`, `delete_task`, `transition_task_status`, and `claim_task`) behave identically, but now with consistency guarantees under concurrent access.
